## API
```
POST /api/count              {delta:±1|±5, uuid, e, g, name?} → {total, dup?, alert?}  // uuid : TEXTE ≤ 64 car. · un refus (400/404) est TOUJOURS du JSON {error} — flush() s'en sert pour distinguer notre API d'un intermédiaire
GET  /api/state?e=X&g=Y      → {total, groupCount, capacity, eventName, groupName}
GET  /api/events?code=X      → {events:[{id,name,total,capacity,groups:[{id,name,count}],createdAt}]}
POST /api/events             {code, name?} → {id, name, total, capacity, groups}  // cloud : 502 {error} si le DO ne s'initialise pas (entrée du registre retirée)
POST /api/groups             {code, e, name?} → {id, name}
GET  /api/history?code=X&e=X[&since=<ms>][&series=fine|coarse] → {history:[{t,c,i,o,g}], historyCoarse:[{t,c,i,o}], total, capacity, peak, totalIn, totalOut, groups:[{id,name,count,totalIn,totalOut,opStats}]}  // c=présents(net) ; i/o=cumuls ; g={groupId:count} ; history=fin 30s/36h ; historyCoarse=5min/60j ; since/series = fenêtrage ; peak = max sur les 2 séries (jamais fenêtré)
GET  /api/clients?code=X&e=X → {clients:[{name,groupName,connectedAt}]}
POST /api/admin/config       {code, e, g?, capacity?, name?, newCode?, newPermCode?, reset?, archived?, deleteGroup?, deleteEvent?} → {ok}  // admin only
POST /api/reset-counts       {code, e} → {ok}  // admin OU perm : count groupes→0, garde historique (+1 pt) + totalIn/out/opStats
GET  /api/qr?code=X&e=X&g=Y  → {qr:dataURL, url}  // 404 si l'événement ou le groupe n'existe pas (local ET cloud) · 500 {error} si la génération échoue
GET  /api/ips?code=X         → {ips:string[], port}  // plus appelé par l'UI (#ip-list masqué, cf. Invariants)
```

## WebSocket
URL : `ws://host/?e=<id>&g=<gid>` (op) · `?e=<id>` (admin/stats). **Code 4004** si l'événement ou le groupe est introuvable, archivé ou supprimé — local ET cloud, à la connexion comme en cours de route (cf. Invariants « Lien mort »).
Backoff reco 1s→…→30s, reset sur succès/switch. `wsReconnectNow()` sur `visibilitychange` (annule timer, tue zombie, reco). Heartbeat : ping 20s, close si silence >60s. Page cachée → pas de timer.

| sens | type | champs |
|---|---|---|
| s→c | `init` | total, capacity, eventName, groups:[{id,name,count}] |
| s→c | `update` | total, delta, alert, capacity, groups |
| s→c | `clients` | clients:[{name,groupName}] |
| c→s | `hello` | name (après chaque onopen) |
| c→s `ping` / s→c `pong` | — | keepalive 20s ; pong immédiat (server.js ET event.js) |

## Invariants critiques
- **State** : `{adminCode, permCode, events:{[id]:{capacity,history,groups:{[id]:GroupState}}}}`. Groupe "Principal" auto-créé. Dernier groupe non supprimable. Event archivé → 404.
- **UUID dedup** scopé par event — protège les retries réseau, pas la multi-porte.
- **Delta** jamais état absolu → concurrent-safe. **Bornage au TOTAL, pas au groupe** : `eff = (total+delta<0) ? -total : delta` puis `grp.count += eff` (server.js + event.js + index.html). Un groupe peut être **négatif** (entrée par un groupe, sortie par un autre) tant que le total event reste ≥ 0. `totalIn/out`/opStats comptés sur `eff`.
- **Le TOTAL n'est jamais négatif, un GROUPE si** (décision Elie, 2026-10-12 : « un groupe peut être une entrée, l'autre la sortie — c'est le compteur global qui doit refuser d'être en négatif »). Le comptage le garantit (bornage). Ce qui le cassait : retirer la part d'un groupe d'ENTRÉE alors qu'un groupe de SORTIE est négatif — `deleteGroup`, ou `reset` d'UN groupe (entrée +5 supprimée, sortie −2 restante → total −2). Or la formule de bornage suppose cur ≥ 0 : avec un total négatif, un clic « −1 » appliquait +|total| et l'inscrivait en ENTRÉES (`totalIn`, `opStats.in`).
  **Règle : le total est ramené à 0** — `floorTotalAtZero(evt)` (server.js) / `_floorTotalAtZero()` (event.js) remonte les groupes NÉGATIFS, le plus négatif d'abord, juste ce qu'il faut ; les groupes positifs et les cumuls (`totalIn/out`) ne bougent pas (personne n'est passé). Appelé après la suppression ou la remise à zéro d'un groupe, **et en tête de chaque comptage** (un état enregistré avant le correctif peut porter un total négatif). Un groupe négatif reste négatif tant que le total est ≥ 0 — ne pas « corriger » ça.
- **Queue localStorage** (PAS dans le service worker : Background Sync n'existe pas sur Safari iOS — `sw.js` ne garde que la coquille, cf. « Coquille hors ligne »). Ancienne queue sans `e` vidée au boot. **UI optimiste** : total + groupe màj avant ack.
- **La file vit en MÉMOIRE, localStorage n'en est que la copie** — `saveQueue()` (index.html) est le SEUL endroit qui l'écrit, sous try/catch. localStorage peut être inutilisable : WebView dont le stockage DOM est désactivé (→ `localStorage` vaut `null`), cookies bloqués, quota. Écrit sans garde dans `tap()`/`flush()`, il levait à chaque appui, et dans `flush()` l'exception était prise pour une panne réseau : la passe s'arrêtait après CHAQUE op → 1 op / 2 s. Ne jamais réécrire `localStorage.setItem('op_queue', …)` en direct.
- **Quand `flush()` jette une op — et quand il ne la jette pas** : une op n'est retirée de la file que si (a) elle est acquittée — réponse 200 en JSON **avec un `total` numérique** — ou (b) NOTRE API la refuse définitivement — **400 ou 404 en JSON avec un champ `error`** (événement archivé, groupe supprimé : elle ne passera jamais et bloquerait les suivantes). **Tout le reste se garde** et se réessaie : 429, 5xx, coupure, délai de 5 s, mais aussi 401 / 403 / 407 / 408… et un 404 en HTML. Ceux-là ne viennent jamais de notre API sur `/api/count` : ils viennent de ce qu'il y a DEVANT (pare-feu ou défi anti-bot Cloudflare, proxy, portail captif d'un Wi-Fi public). L'ancienne règle « tout 4xx ≠ 429 → `shift()` » perdait ces comptages en silence. Conséquence assumée : une op refusée sans JSON bloque la file — mais le badge « N en attente » le montre, alors qu'une op jetée ne laisse aucune trace. **Côté serveur : un refus de `/api/count` doit rester du JSON `{error}`.**
  L'accusé de réception d'une op d'un AUTRE événement (restée en file avant un changement de lien) ne touche pas au total affiché (`op.e === EVENT_ID`).
- **Aucune attente sans limite dans une page — le blocage du 2026-10-13.** Constaté par Elie (navigateur DuckDuckGo ; la production servait alors `c40c921`) : après une coupure, les appuis restaient « N en attente » pour de bon, les nouveaux s'y ajoutaient, alors que les comptages des AUTRES continuaient d'arriver — il fallait recharger la page.
  **Cause** : `fetchWithTimeout()` arrêtait sa minuterie à l'arrivée des EN-TÊTES et laissait `await res.json()` sans aucune limite. Une réponse de `/api/count` dont le corps n'arrive jamais (réseau qui tombe ou sature en cours de réponse) ne se terminait donc jamais, et le verrou booléen de `flush()` restait pris : plus rien ne partait. Le WebSocket, lui, n'en dépend pas. Reproduit dans WebKit (`npm run test:webkit`) : bloqué plus de 110 s, **pas débloqué par le retour du réseau**, débloqué par un rechargement. Aucune autre panne essayée ne bloque la file (réseau coupé, réseau muet, navigateur qui se croit hors ligne : vidée en 1 à 6 s).
  **Pas de doublon** : l'op dont la réponse s'est perdue ÉTAIT comptée côté serveur tout en restant « en attente » à l'écran (d'où l'impression de double comptage) ; renvoyée avec le même uuid, elle revient `dup`. Total serveur == nombre d'appuis dans tous les essais.
  **Correctif — écran opérateur** : `requestJSON()` borne la requête ENTIÈRE (5 s pour les en-têtes, puis 5 s pour le corps), et ce délai tient à une minuterie de la PAGE (`Promise.race`), pas à la seule bonne volonté d'`abort()`. Le verrou de `flush()` est un **bail** (`flushAlive` = heure de la dernière avancée, caduc après `FLUSH_STALL_MS` = 15 s ou si l'horloge recule ; `flushPass` arrête une passe remplacée) : seconde ceinture pour une page figée en arrière-plan ou une attente ajoutée un jour dans la boucle. `dequeue(op)` retire CETTE op, jamais « la première » (l'accusé tardif d'une passe remplacée jetterait la suivante). La minuterie de 2 s **ne consulte plus `navigator.onLine`** (avis du navigateur : resté à « hors ligne », la file attendait la réouverture du WebSocket, jusqu'à 30 s). `/api/state` au démarrage passe par le même utilitaire — sinon `connect()`, donc le WebSocket, n'était jamais appelé.
  **Correctif — admin.html et stats.html** : même trou dans `fetchT()` (code IDENTIQUE dans les deux pages, un test le vérifie). Le corps y est lu par morceaux, le délai de 6 s **repartant à chaque morceau** (un historique de 1,6 Mo sur réseau lent peut durer ; rester 6 s sans rien recevoir, non) ; rend `{ ok, status, json() }`. Sur stats, c'est `liveStatsBusy` qui restait pris : tableaux par groupe / par opérateur figés jusqu'au rechargement.
  **Règles** : (1) un seul `fetch()` par page, dans son utilitaire (test statique) ; (2) ne jamais arrêter un délai à l'arrivée des en-têtes ; (3) un verrou tenu pendant un `await` doit pouvoir expirer.
  **Pas établi** : ce qui a fait caler un corps chez Elie. Une vraie coupure de réseau ne se simule pas ici, et la prod envoie en-têtes et corps ensemble (0,15 ms d'écart mesuré ; WebKit lui parle en HTTP/2). Le diagnostic tient par élimination (seule attente illimitée de `flush()`) et par la concordance exacte des symptômes — **à confirmer dans DuckDuckGo après déploiement**. Si la file y reste LENTE à se vider (tentatives qui expirent en boucle sur une connexion HTTP malade pendant que le WebSocket marche), la suite logique est d'envoyer les comptages par le WebSocket quand il est ouvert — changement de protocole (local + cloud), pas fait.
- **Broadcast** : un JSON par event, chaque client extrait son groupe en JS → O(1).
- **Plafonds (R4)** : `MAX_EVENTS=50` (archivés inclus) · `MAX_GROUPS=20`/event · `MAX_OPS=100`/groupe (opStats) · `MAX_HISTORY=4320` (fin, **36h@30s**) · `MAX_HISTORY_COARSE=17280` (grossier, 60j@5min) · `MAX_UUID_LEN=64` (uuid d'une op : 36 ou ~40 car. ; au-delà → 400 — les uuid sont persistés, 2 500 dans UNE clé DO de 2 Mo) · seenOps trimmé 20k→10k. Dépassement création → **409**. opStats au plafond : nom ignoré mais **comptage jamais bloqué**. Constantes dupliquées cloud (registry/event.js) + local (server.js) — garder alignées.
- **Rate-limit (S3/L3)** : token bucket par IP `RL_CAPACITY=300` burst · `RL_RATE=20`/s, en tête de `/api/count` cloud (`_rl_check`, `cf-connecting-ip`) ET local (`rlCheck`, `req.ip`). Dépassement → **429 + Retry-After**. **Le client ne jette JAMAIS un 429** : `flush()` fait `break` et relance (sinon perte). Buckets alignés.
- **Rôle PERM** : `permCode` distinct — UI masque capacité/reset-event/archive/codes/groupes-edit (mais reset-counts autorisé).
- **Net vs cumuls (i/o)** : `c` = **présents** (somme des counts) → un −1 le fait redescendre. Les entrées cumulées ne sont donc PAS déductibles de la courbe : chaque point (fin ET grossier) porte `i`/`o` = `Σ totalIn`/`Σ totalOut` de l'event à cet instant (`cumulIO()` local / `_cumulIO()` cloud). Invariant : `i − o === c`, **sauf après un reset-counts** (c repart à 0, i/o continuent) **ou la suppression / remise à zéro d'un groupe** (sa part quitte c, et le total peut être ramené à 0). Points d'avant la feature : `i`/`o` **absents** — jamais remplacés par 0 (export → cellule vide, chart → `null` + `spanGaps`), et non reconstituables rétroactivement.
- **Historique par groupe — cadence 30 s, rétention 36 h** : point `{t, c, i, o, g:{[gid]:count}}` toutes les **30 s** (`FINE_INTERVAL_MS`), plafond `MAX_HISTORY=4320` → **36 h de détail**.
  **Besoin métier** : sortir un événement de 24 h point par point toutes les 30 s (2880 points). Le plafond est à 4320 et non 2880 parce qu'un event **non archivé continue d'être échantillonné** : à 2880 (= pile 24 h) le buffer glisse d'**une heure du DÉBUT de l'événement par heure d'attente avant l'export** (mesuré). 36 h = 24 h d'événement + **12 h de marge pour exporter**.
  **Archiver en fin d'événement FIGE la série fine** (`recordHistory`/`alarm()` sautent les events archivés) → plus aucune limite de délai. C'est la bonne pratique d'exploitation.
  Mesuré : série pleine = **1,34 Mo à 20 groupes** (limite DO 2 Mo/clé, marge 33 %), **alarme 6 ms** dans workerd, sauvegarde locale 9–40 ms. Dérive `setInterval` ~1,6 ms/tir → ~5 s cumulées sur 24 h, sans effet sur l'export (les points portent `Date.now()` réel). **Local** : `evt.history` (state.json) via `recordHistory()`. **Cloud** : clé DO **séparée `history`** (≠ `state`), écrite seulement par l'`alarm()` → `_save()` léger ; `_load()` migre l'ancien inline (waitUntil). `stats.html` trace `history[].g[gid]` (`spanGaps:true` ; `g` absent → `null`), affiché si >1 groupe.
- **Historique grossier (rétention 60j)** : série **total seul** `{t,c}` toutes les 5 min, plafond `MAX_HISTORY_COARSE=17280` = 60 j. **Local** : `evt.historyCoarse` via `recordHistoryCoarse()` (setInterval 5min). **Cloud** : clé DO **séparée `historyCoarse`**, alimentée par l'`alarm()` (30s) seulement si ≥5min écoulées depuis le dernier point. reset/reset-counts ajoute/vide aussi le grossier. **Backfill** : event antérieur à la feature (clé absente) → série grossière reconstruite depuis l'historique fin via `downsampleCoarse()` (1 pt/bucket 5min, jusqu'à 36h dispo) au `_load()` cloud / `backfillCoarse()` local (au boot + lazy dans `/api/history`). Données au-delà de la fenêtre fine jamais stockées → non récupérables.
- **Export XLSX = les 2 séries fusionnées** : l'onglet « Historique » concatène le grossier (`t < history[0].t`, colonne Série = « long terme ») puis le fin (« détaillé ») → l'export couvre jusqu'à **60 j**, pas seulement la fenêtre fine. Le filtre `< cutoff` évite les doublons sur la zone commune. Colonnes : Horodatage · **Présents** · Entrées cumulées · Sorties cumulées · Série. L'onglet « Résumé » porte la période couverte, la résolution de chaque série et la note de lecture net/cumuls.
- **Budget stockage DO (2 Mo par clé, SQLite-backed)** : mesuré ≈ 1 Mo pour `historyCoarse` (17280 pts) et **1,34 Mo pour `history`** (4320 pts × ~307 o à 20 groupes) → marge 33 %. **Tout nouveau champ par point se paie ×4320 (fin) et ×17280 (grossier)** — remesurer avant d'en ajouter un, la marge n'est plus de 2×.
- **Chart stats : fenêtre + live (pas de push/clic)** : 2 séries — `fullHistory` (fine 60s, ≤48h, avec groupes) et `fullHistoryCoarse` (grossière 5min, total seul). `selectedSeries()`/`usesFineSeries()` : fenêtre ≤ **`FINE_RETENTION_H=36`** → fine ; au-delà → grossière. La vue **48 h passe donc en grossière** (5 min, sans lignes par groupe) puisque la fine ne couvre plus que 36 h. `FINE_RETENTION_H` = `MAX_HISTORY × FINE_INTERVAL_MS` : **constante dupliquée à réaligner si la cadence change**. Le WS `update` ne pousse PLUS un point/clic : `updateLivePoint()` déplace le DERNIER point (« maintenant »). `setInterval` 60s re-fetch `/api/history` (fine+grossière) → la fenêtre glisse.
- **Courbe « Entrées cumulées » (stats)** : dataset sur un **2e axe Y à droite** (`y1`, `display:'auto'` → l'axe n'apparaît que si la courbe est affichée), **masqué par défaut**, révélé par un clic sur la légende. `showCumul` mémorise le choix car `renderChart()` détruit/reconstruit le graphe (fenêtre + refresh 60s) ; `legend.onClick` appelle le handler Chart.js par défaut puis relit `isDatasetVisible()`. `totalIn` suit le live via `+delta` sur `update` WS et se **resynchronise** à la relecture en direct (≤ 1 s après un clic, cf. « Stats par groupe / par opérateur en direct ») et au fetch 60 s (le `+delta` dérive si le total est borné à 0).
- **Stats par groupe / par opérateur en direct (stats.html)** : avant, `renderGroups`/`renderOpStats` n'étaient appelés qu'à l'ouverture de la page → entrées/sorties par groupe et chiffres par opérateur restaient **figés** pendant que les tuiles du haut bougeaient (seul le `count` des groupes suivait, retouché ligne par ligne dans le DOM ; un groupe créé après coup n'apparaissait pas).
  **Le détail par opérateur ne passe PAS par le WS** : le WS n'est pas authentifié (S5 — quiconque connaît l'id de l'événement le lit), alors que ces chiffres sont derrière le code (`/api/history`). `update` reste `{type,total,delta,alert,capacity,groups:[{id,name,count}]}` — **clés figées par un test, local ET Worker** : tout nouveau champ doit être pesé pour un canal ouvert.
  À la place, chaque `update` appelle `scheduleLiveStats()` → relecture **minimale** `/api/history?series=fine&since=<maintenant>` (aucun point d'historique : groupes, opStats et cumuls seulement, ~650 o pour 3 opérateurs) — au plus 1/s (`LIVE_STATS_MIN_MS`), jamais deux en parallèle, une dernière après la rafale. **Ne jamais passer cette réponse à `applyHistory()`** : elle remplacerait la série affichée par un tableau vide.
  `statGroups` = dernier relevé faisant foi ; `liveGroups()` y superpose le `count` du WS (en avance d'une requête — sinon un count recule d'un cran) ; `applyGroupStats()` est appelé par TOUS les fetchs (ouverture, WS `init`, changement de fenêtre, refresh 60 s, relecture en direct). Le cumul « Entrées » est resynchronisé par la relecture **sauf si un clic est arrivé pendant la requête** (réponse en retard sur le WS → la tuile reculerait). Page cachée → aucune relecture ; le WS `init` du retour au premier plan resynchronise.
  Mesuré (navigateur intégré, état isolé) : 1 clic → ligne de l'opérateur à jour sans recharger ; 20 clics en 1,3 s (2 opérateurs, 2 groupes) → 3 relectures, 0 recul de la tuile, page == serveur ; « Compteurs à zéro », remise à zéro d'un groupe, nouveau groupe et renommage suivis sans recharger. **Piège de test** : dans le navigateur intégré `document.hidden` vaut `true` (panneau masqué) → la relecture ne part pas ; redéfinir `document.hidden` le temps de l'essai.
- **Axe X temps réel (linéaire)** : `scales.x.type='linear'` sur des points `{x:ts, y}` (PAS d'axe catégoriel) → un pas de 30 min se voit comme 30 min, les trous comme des trous. Pas d'adaptateur de date (timestamps bruts). `ticks.callback=fmt(v)` : `fmt()` = date si vue longue (`chartWindowH===0 || >48`), date+heure en 48h (à cheval sur 2 jours), heure sinon. Tooltip `title` = date+heure complète. Ligne capacité = 2 points `[premierX, maintenant]`. `updateLivePoint` remplace le dernier `{x,y}` de chaque dataset.
- **Persistance DO seenOps** : `_load()` lit `seen`, `_save()` persiste `[..._seen].slice(-2500)`. Local : `buildSnapshot`/`applySnapshot` sérialisent seenOps (max 5000/event) ; `scheduleSave()` debounce 500ms + `setInterval(flushSave,30000)`.
- **Écriture atomique de `state.json`** : `flushSave()` fait `openSync(.tmp)` → `writeSync` → **`fsyncSync`** → `closeSync` → **`renameSync`**. Un `writeFileSync` direct laissait un JSON tronqué si le process mourait pendant l'écriture (elle a lieu toutes les 30 s **et** 500 ms après chaque comptage → fenêtre large) : au boot `JSON.parse` throw, l'état repartait à vide **et était écrasé 30 s plus tard** = soirée perdue. En cas d'échec : `.tmp` supprimé, `state.json` précédent laissé intact. Au boot, un `state.json` illisible est **renommé `.corrupt-<ts>`** au lieu d'être écrasé.
- **`STATE_FILE` surchargeable par `process.env.STATE_FILE`** : la suite locale importe `server.js` et `/api/count` déclenche `scheduleSave()` → sans ça `npm test` **écrasait le `state.json` d'exploitation** avec ses fixtures. `tests/server.test.js` pose `process.env.STATE_FILE` vers un `mkdtemp` **avant** le `require('../server')` — ordre critique, la constante est lue à l'import.
- **`run_worker_first: true` OBLIGATOIRE** (wrangler.jsonc) : sinon Workers Assets sert `index.html` (200) avant le Worker → l'upgrade WS reçoit du HTML au lieu du 101 → opérateurs hors ligne en prod. Vérif : `curl -i --http1.1 -H "Upgrade: websocket" …/?e=x&g=x` → 404 `text/plain` (id mal formé : refusé par le Worker), jamais du HTML. Avec un id bien formé, le DO répond 101 (puis ferme en 4004 si l'événement n'existe pas).
- **Alerte de capacité : elle part chez TOUS les opérateurs** — le WS `update` appelle `setCount()`, qui appelle `triggerAlert()`. Aucun code dédié à écrire pour « prévenir tout le monde ».
  **`navigator.vibrate` n'existe sur AUCUNE version de Safari iOS** : sur iPhone la vibration ne part jamais, silencieusement (le `if (navigator.vibrate)` masque l'absence). Effet de bord assumé : plus d'auto-remplissage par le trousseau. **Vérifié** en navigateur (DOM sans `input[type=password]` ni `<form>`, masquage, 3 parcours de connexion, repli) mais **pas la fenêtre native** (absente du navigateur intégré, pas de simulateur iOS) → à confirmer sur iPhone.
- **Adresses réseau (`#ip-list`) masquées → `loadIPs()` est un no-op** : le `<div id="ip-list">` est **commenté** dans admin.html depuis `f6e083c` (Elie, 16/06, « minor changes admin »), mais `loadIPs()` continuait de l'appeler (connexion sans événement + `onopen` du WS admin) → `TypeError` « reading 'dataset' » (promesse rejetée, sans effet visible) à chaque fois, pendant ~3 mois. Corrigé par un garde `if (!el || …) return` **avant** le fetch (aucune requête `/api/ips`). **Décommenter le div suffit à réactiver l'affichage** (vérifié, dont le repli `origin` sur le cloud). Masquage à respecter tant qu'Elie ne demande pas le contraire : ne pas restaurer le div ni supprimer le garde.
- **Logos pages** : `.logo-bar` en tête de `admin.html` + `stats.html` (`#logo-dark`/`#logo-light`, switch `@media prefers-color-scheme`, height 28px). Export XLSX : pas de logo (SheetJS gratuit ne supporte pas les images).
